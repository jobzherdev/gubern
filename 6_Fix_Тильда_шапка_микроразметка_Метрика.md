# Фикс: съезжает шапка сайта в Тильде. Разбор поля «Вставка кода в HEAD»

**Проект:** festivalcontest.ru (ООО «Губерния», ИНН 4217147207)
**Симптом:** вверху страницы пустая полоса, шапка уезжает вниз, строка контактов наезжает на H1
(особенно на мобильных).
**Статус:** причины найдены по полному содержимому поля HEAD. Ниже — разбор и готовый код на замену.

---

## 1. Найденные ошибки

### 1.1. Корневая причина: `<noscript><div>` внутри `<head>`

По стандарту HTML, при **включённом** JavaScript содержимое `<noscript>` внутри `<head>`
разбирается в режиме **«in head noscript»**, где разрешены только `link`, `meta`, `style`,
`basefont`, `bgsound`, `noframes`. Теги `<div>` и `<img>` там запрещены. Встретив `<div>`, парсер:

1. закрывает `<noscript>`;
2. **закрывает `<head>`**;
3. **открывает `<body>`**;
4. вставляет этот `<div>` первым элементом страницы.

В текущем коде таких блоков четыре — после каждого счётчика (Метрика ×2, Top.Mail.Ru, VK).
Срабатывает первый же.

Последствия:

- в самом начале `<body>`, выше всей вёрстки Тильды, появляется посторонний `<div>` с картинкой;
- **весь код ниже первого `<noscript>` оказывается внутри `<body>`**: остальные счётчики, пиксель
  VK, JSON-LD и служебный `<head>`, который Тильда выводит после пользовательского поля;
- если в этот «выселенный» хвост попадает `<meta name="viewport">`, браузер его игнорирует —
  мобильная вёрстка считается по десктопной ширине. Отсюда несоразмерно крупный H1, вылезающий за
  экран, и наезд контактов на заголовок;
- сбивается расчёт компенсирующего отступа под фиксированную шапку Тильды.

Яндекс в документации разрешает ставить счётчик в head, и обычно это сходит с рук: картинка
спрятана через `position:absolute; left:-9999px`, разрыв документа проходит незаметно. Здесь не
сошло из-за ошибки 1.2.

### 1.2. `&quot;` вместо кавычки в первом `noscript`

```html
<img src="https://mc.yandex.ru/watch/111198518&quot; style="position:absolute; left:-9999px;" alt="" />
                                              ^^^^^^
```

`&quot;` — HTML-сущность, а не разделитель. Значение `src` на ней не заканчивается и тянется до
следующей настоящей кавычки — той, что после `style=`. В результате:

- `src` = `https://mc.yandex.ru/watch/111198518" style=` — битый URL;
- `position:absolute;` и `left:-9999px;"` — мусорные атрибуты без значений;
- **атрибут `style` теряется полностью.**

Картинка, которая должна была уехать за левый край экрана, рисуется в потоке как плейсхолдер
«сломанное изображение».

### 1.3. Первый счётчик Метрики не работает вообще

В инициализаторе счётчика `111198518` потеряны операторы `||`:

```js
m[i]=m[i]function(){(m[i].a=m[i].a[]).push(arguments)};   // как сейчас — синтаксическая ошибка
m[i]=m[i]||function(){(m[i].a=m[i].a||[]).push(arguments)}; // как должно быть
```

Это ошибка парсинга JavaScript, а не рантайм-исключение, поэтому **не выполняется весь блок
`<script>` целиком** — вместе со строкой `ym(111198518, 'init', …)`. Счётчик `111198518` никогда
не собирал данные. Во втором блоке (`88246468`) те же `||` на месте, там код рабочий.

### 1.4. Белую полосу 180 px рисует самодельный CSS

В конце поля HEAD:

```css
@media screen and (max-width:640px){
  #allrecords{ padding-top:180px !important; }
  #rec1258557471 .t396, #rec1258557471 .t396__artboard{ top:0 !important; }
}
```

Это костыль, которым компенсировали съехавшую шапку. Он и создаёт пустой блок над шапкой на
мобильных. После устранения причин 1.1–1.2 его нужно удалить, иначе полоса останется навсегда.

### 1.5. Прочее

| Что | Где | Проблема |
|---|---|---|
| `pid: "USER_ID"` | Top.Mail.Ru, `_tmr.push` | Незаменённая заглушка из документации, шлёт мусорное значение |
| Два счётчика Метрики | `111198518` и `88246468` | После фикса 1.3 оба станут рабочими → данные задвоятся |
| `festivalcontest.net` | `@id` и `url` в JSON-LD | Домен не совпадает с почтой в контактах (`@festivalcontest.ru`) |
| `tag.js` без `?id=` | второй счётчик | Лучше `tag.js?id=88246468` — конфигурация отдаётся сразу под нужный счётчик |

## 3. Два счётчика Метрики на одной странице

По решению клиента оба счётчика — `111198518` и `88246468` — остаются рабочими. Это штатный
сценарий Метрики, ограничений на количество счётчиков нет. Но держать их **двумя копиями
загрузчика нельзя**.

### Почему

В сниппете есть защита от повторной загрузки библиотеки:

```js
for (var j = 0; j < document.scripts.length; j++) {if (document.scripts[j].src === r) { return; }}
```

Она сравнивает **точное совпадение `src`**. В исходном коде у двух блоков разные URL —
`tag.js?id=111198518` и `tag.js` — проверка не срабатывает, и `tag.js` грузится дважды: лишний
сетевой запрос и повторная инициализация одной и той же библиотеки.

Правильная схема — **один загрузчик, два вызова `init`** (реализована в коде п. 2). Загрузчик взят
без `?id=`: это универсальный URL библиотеки, и в общем загрузчике на два счётчика номер одного из
них выглядел бы произвольным. Параметры каждого счётчика настраиваются независимо, в своём вызове
`ym(ID, 'init', {...})`.

### Что нужно проверить

**1. Поле Настройки сайта → Аналитика → Яндекс.Метрика должно быть пустым.** Если там вбит номер,
Тильда вставит собственный сниппет — получится третья копия и задвоенные хиты по этому счётчику.

**2. Цели уходят только в тот счётчик, который указан явно.** Вызов
`ym(111198518, 'reachGoal', 'form_sent')` засчитается только первому счётчику. Если конверсии
нужны в обоих, каждую цель дублировать:

```js
ym(111198518, 'reachGoal', 'form_sent');
ym(88246468,  'reachGoal', 'form_sent');
```

Штатная интеграция Тильды с формами отправляет цель только в счётчик из настроек сайта — а он у
нас пустой (см. п. 1). Значит, цели навешиваются вручную и на оба ID.

**3. Вебвизор включён на обоих счётчиках** — сессии пишутся дважды, это удвоенный объём записей и
лишняя нагрузка на страницу. Если второй счётчик нужен только для сводной статистики, у него
`webvisor:true` стоит убрать.

**4. Историчность данных.** Из-за синтаксической ошибки (п. 1.3) счётчик `111198518` не работал
никогда — вся накопленная статистика лежит в `88246468`. После фикса `111198518` начнёт собирать
данные с нуля, и первое время отчёты по двум счётчикам будут несопоставимы. Это ожидаемо, не баг.

## 4. Порядок действий

1. Заменить содержимое поля HEAD на код из п. 2.
2. Убедиться, что блок `<style>` с `padding-top:180px` удалён.
3. Проверить, что поле Настройки сайта → Аналитика → Яндекс.Метрика пустое (п. 3).
4. Сохранить → **«Опубликовать все страницы»**: код HEAD запекается в каждую страницу отдельно,
   иначе на части URL останется старая версия.
5. Проверить с обходом кэша (`?v=1`) на десктопе и мобильном.

## 5. Правила вставки кода в Тильде (на будущее)

| Что | Куда | Почему |
|---|---|---|
| Счётчики, пиксели, JSON-LD | Настройки сайта → Ещё → **HTML-код внутрь head** | Допустимы только `<script>`, `<meta>`, `<link>`, `<style>` |
| Любые `<noscript>`, `<img>`, `<div>`, `<iframe>` | Настройки сайта → Ещё → **HTML-код внутрь body** | В head они разрывают документ (п. 1.1) |
| Разметка под конкретную страницу (Event, FAQPage, BreadcrumbList) | Настройки **страницы** → Дополнительно → HTML-код внутрь head | Разметка страницы живёт на своей странице |
| Метрика без кастомных параметров и в единственном экземпляре | Настройки сайта → Аналитика → Яндекс.Метрика (только номер) | Тильда подставит корректный сниппет сама. **Не использовать одновременно с ручной вставкой в HEAD** — получится дубль |

**Никогда** не вставлять счётчики и микроразметку в блок T123 «HTML-код», в элемент «HTML» внутри
Zero Block или в текстовый блок: T123 — полноценная запись страницы со своими паддингами, она даёт
пустую полосу 20–60 px, а элемент Zero Block резервирует место абсолютным позиционированием.

Кавычки — только прямые `"`. Не переносить код через Word и Google Docs: они превращают кавычки в
«ёлочки», а операторы вроде `||` и неразрывные пробелы могут потеряться при копировании через
редакторы и мессенджеры — именно так появилась ошибка 1.3. После вставки любого счётчика
открывать консоль браузера и проверять, что нет `SyntaxError`.
